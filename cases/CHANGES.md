## v1→v2（try1 の後）
1. **Y-02 の入力（保存完了時刻）だけを変更**。差分は cases/v1-to-v2.diff（1行）。
   - 理由：設計 v0.3 の Y-02 が指定するのは「開催日 2099-12-30」「発表月日時分 01011000」と期待値「2100-01-01 10:00 として採用」だけ。保存完了時刻は設計に書かれておらず、のあが「開催日 11:00」と仮に置いた。その値は採用した発表時刻（2100-01-01 10:00）より前になり、U-01 の規則（発表が保存完了より後は矛盾として隔離）に当たる。これは試したい性質（年の補完）とは別の、入力の作り方の誤り。
   - 変更：保存完了を 2100-01-01 10:01（発表の1分後）にした。期待値は v1 のまま。
   - 設計への注記（v0.4 で見直す候補）：Y-02 は「開催日より後に発表された中間オッズ」という現実には起きない組合せ。年の補完の試験としては成り立つが、入力例として不自然。
2. **判定の追加ゲート G3b（同じ System へ同じ事象をもう一度流す）を、合否から外して別記にした**。
   - これは設計の全体基準3（同じ入力で2回流して同じ）より厳しく、のあが独自に足した確認。設計の基準3は G3a（新しい System で2回流して完全一致）で判定している。
   - try1 で D-01a だけが G3b で不一致。原因：ケースの事象が時刻順でない（11:16 の観測を 11:15 の確定より前に並べている）。もう一度流すと 11:16 の観測が「最終確定後に届いた別の値」として扱われ、F-01 と同じ規則で警告が1件出る。仕組みの動きとしては正しい。
   - 結果は results.json の extra_G3b_replay_ng に必ず出し、完了報告にも書く。
